# TECH

Status: Living document. Never edit autonomously — confirm with user first.

---

Stack_Frontend: Vanilla JavaScript (ES6+), HTML5, CSS3. No UI framework (no React/Vue/Angular). Vite as dev server and bundler.
Stack_Backend: Vercel Serverless Functions (Node.js) back the two dynamic features: `api/yatsy/games/*` is the server-side authority for Yatzy matchmaking/real-time state sync, and `api/track.js` + `api/admin/stats.js` record and aggregate hub launch counts. The rest of the site remains static.
Database: No general-purpose database. Game content is static JSON shipped in `public/data/` and `public/hub-config.json`. Supabase (Postgres) stores only ephemeral Yatzy room state and append-only hub launch events (see `docs/DATA_MODEL.md`), using the shared `multigames-db` Supabase project (also used by `coinchapp`), with tables namespaced (`yatzy_*`, `muchogames_*`) to avoid collisions.
Runtime: Node.js for tooling (Vite, ESLint, Prettier, CI) and for the `api/yatsy/games/*` serverless functions. Browser runtime for the app itself.
Package_Manager: npm
Hosting: Vercel, serving the Vite build output (`dist/`) plus the `api/` serverless functions from the same project. Must stay within the free Hobby plan. Also reachable via the custom domain `muchogames.win` (purchased by the user, DNS through Cloudflare, pointing at the same Vercel project) alongside the default `bergamots.vercel.app`.
Authentication: No accounts for players. The hub (`auth.js`, hub-only, not loaded by any game) offers Google Sign-In via Google Identity Services (`https://accounts.google.com/gsi/client`), loaded and run entirely client-side. The JWT credential Google returns is never verified or transmitted anywhere; it is decoded client-side (base64, no signature check needed since nothing trusts this value for access control) solely to read the `email` claim, which is stored in `localStorage` (`bergamots-auth`) so it can be shown in the popover and survive a reload. No backend endpoint, no cookie, no server-side session — the email never leaves the browser. `GOOGLE_CLIENT_ID` (a constant in `auth.js`) is not a secret — like the Supabase anon key, it is meant to be public and is restricted by its Authorized JavaScript origins (`bergamots.vercel.app`, `localhost:5173`, `muchogames.win`), not by secrecy; Vercel preview URLs are not in that list, so the button does not render on previews. When signed in, the popover also links to `/profile` (`public/profile/`, same unbundled static-page pattern as `public/admin/` — no `vite.config.js` entry, clean URL only in production). Logging out only clears the local flag and calls `disableAutoSelect()`; it does not revoke the underlying Google session. See `docs/DECISIONS.md` 2026-09-05.
Profile page (`public/profile/index.html` + `profile.js`): one text field ("Nom"), saved to `localStorage` (`bergamots-player-name`) on submit. Client-only, no backend. Not yet read by any game — the intent is to later pre-fill each game's name input from this value, but that consumer code does not exist yet.
The admin page posts the shared password once to `POST /api/admin/login`, which compares it against the `ADMIN_PASSWORD` env var inside `api/_lib/adminAuth.js` using `crypto.timingSafeEqual`, then returns a self-contained 1h token (`expiry.nonce.HMAC-SHA256`, keyed by that same password). `POST /api/admin/stats` accepts only the token, so the password is never replayed on reads and never kept in the browser. No accounts, no user records, no server-side session store. Because the password doubles as the signing key, rotating it invalidates live sessions. It protects read-only aggregate counts, nothing else.
Authorization: Capability-based, not identity-based. Yatzy multiplayer access is gated only by a 3-letter room code plus a per-seat resume token, enforced server-side by `api/yatsy/games/*` plus Supabase RLS blocking all direct client access. Admin stats access is gated by the short-lived token exchanged for `ADMIN_PASSWORD`. `POST /api/track` is intentionally unauthenticated, so launch counters can be inflated by anyone who finds the URL; an in-memory throttle (60 events per minute per IP) raises the cost without pretending to prevent it, since its state is per warm serverless instance and resets on cold start.
Security: No secrets committed. `.env*` files are ignored (see `.env.example`). Supabase client config (`public/games/yatsy/supabase-config.js`, URL + anon key) is public, not a secret — protected by Row Level Security, not secrecy. `SUPABASE_SERVICE_ROLE_KEY` and `ADMIN_PASSWORD` are server-only, set as Vercel env vars, never committed. The admin password is never sent to the browser: the browser posts a candidate and the function answers with a token, never with the password. `vercel.json` carries the HTTP hardening: `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: SAMEORIGIN` and a `Permissions-Policy` denying camera/microphone/geolocation/payment/usb site-wide, `Cache-Control: no-store` on `/api/*`, and a strict CSP on `/admin` (`default-src 'none'`, `form-action 'none'`, `frame-ancestors 'none'`).
Testing: No automated test suite currently. CI enforces lint, format-check, and build only.
Deployment: GitHub Actions CI (`.github/workflows/ci.yml`) runs `npm run lint`, `npm run format:check`, `npm run build` on push/PR to `main`/`master` (does not deploy). Actual deployment is Vercel's own Git integration: every push to `main` auto-deploys to production (`https://bergamots.vercel.app`), independent of the GitHub Actions CI.

Conventions:
- Language: English for code, filenames, comments, and docs. In-game copy is multilingual (FR/EN/ES) via JSON fields.
- Naming: kebab-case for game ids and folders (`public/games/<id>/`); camelCase for JS identifiers.
- Formatting: Prettier (`.prettierrc`) and ESLint (`eslint.config.mjs`) are the enforced source of truth. Run `npm run format` / `npm run lint`.
- Error_Handling: Formalized for the serverless side, ad-hoc for the browser. `api/_lib/http.js` is the single pattern: every handler is wrapped in `withErrorHandling`, 4xx messages are returned as written because they are meant for the user, and 5xx detail (usually a raw Postgres message) is logged and replaced by one generic sentence. Client-side code still follows per-module style (e.g. `matchmaking.js` throws tagged `Error` objects with a `.code`).
- Logging: Structured on the serverless side — 5xx failures go to stderr as one-line JSON (`level`, `code`, `method`, `detail`, `stack`) and surface in Vercel's runtime logs, which already tag the invocation, path and request id, so no correlation id is added. The browser side is console-only, with no error reporting.

Architecture_Principles:
- Hub-spoke: a central hub (`index.html` + `hub.js`) reads `public/hub-config.json` and links out to standalone, full-page game apps.
- Config over code: adding a wordpack game only requires a data JSON under `public/data/<id>/` plus a `hub-config.json` entry — no changes to `hub.js` or `vite.config.js`.
- Shared code lives in `shared/js/` (`engine.js`, `dom.js`) and `shared/css/` (`base.css`, `wordplayer.css`), reused by the wordplayer engine and by games that opt in (e.g. Olé Mains).
- Each custom game is isolated in its own `public/games/<id>/` folder; no forced code sharing beyond `shared/`. The admin page follows the same pattern in `public/admin/`: plain unbundled HTML/CSS/JS, so it needs no `vite.config.js` entry. It is served at `/admin` in production and at `/admin/index.html` under `npm run dev`. Since `/admin` carries no trailing slash, the page must reference its own assets absolutely (`/admin/admin.css`, `/admin/admin.js`) — relative paths resolve against the site root and 404. Charts are hand-written SVG (`public/admin/trend-chart.js`), because a page with no build step could only pull in a charting library as another unpinned CDN import.
- Analytics is instrumented in one place only (a click listener on hub tiles in `hub.js`, via `shared/js/analytics.js`), never inside individual games. Every game is launched from the hub, so one hook covers them all.
- Full browser navigation between games (`window.location.href`), no SPA router. The browser's own teardown (garbage collection on navigation) handles cleanup between games.
- Keep the system understandable. Avoid premature abstraction. Prefer explicit over implicit. Document non-obvious decisions in `docs/DECISIONS.md`.

Open_Questions:
- Error handling and logging are formalized for `api/` but not for the browser — decide if/when a client-side crash should be reported anywhere instead of dying silently in the player's console.
- No automated tests — decide if/when to add coverage (Yatzy scoring in `scoring.js` and `shared/js/engine.js` are the highest-value candidates).
- Known duplication: rules-modal loading logic (`loadRulesIfExists`-style) is reimplemented similarly across several games instead of shared once.
