Before that: set `ADMIN_PASSWORD` on Vercel Production as a Sensitive variable via `vercel env add --value --sensitive`, then chased why login still answered 500. Two false leads first: a `vercel redeploy` of the existing production deployment did not help, and neither did a full fresh `vercel --prod` build, so the "env vars are snapshotted at build time" theory was wrong. Reading the runtime logs settled it in one shot - which is the observability work from priority 3 paying for itself. The real fault was a genuine bug in `readJsonBody`: it guarded `JSON.parse` but not the `req.body` access above it, and on Vercel's Node runtime `req.body` is a getter that parses eagerly and throws `Invalid JSON`, so the guard was unreachable and every POST with a malformed body answered 500 while logging an `unhandled` error. Fixed in `e070ae9` by guarding the access itself; verified live that a garbage body and an empty body now both give 401 on login and 400 `invalid-event` on `/api/track`, with the correct password still returning a token. Also verified the admin chain properly: correct password gives 200 + signed token, wrong password 401, a token with four characters of its HMAC altered 401, and a valid token passes the gate and only then fails on the missing table. Note my first curl attempts were themselves sending malformed JSON, because PowerShell strips double quotes when passing arguments to native executables - use `-d '{\"k\":\"v\"}'` or `--data-binary "@file"`. Discovered while listing env vars that `SUPABASE_URL` is set on Production only while `SUPABASE_SERVICE_ROLE_KEY` covers Preview too, so every DB-backed route 500s on Preview deployments; both values are Sensitive and therefore unreadable, so only the user can copy it across.
